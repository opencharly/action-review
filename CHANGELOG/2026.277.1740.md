## Summary

**This repo's `tag-on-merge` dispatcher is a laggard copy of an org cutover every other repo already took, and that is why PR #17's merge produced no tag.**

The dispatcher in this repo is md5 `cb385edf8f3c` — the pre-RCA design with **no `wait-for-merge` readiness probe**. The org reference, `opencharly/.github/.github/workflows/tag-on-merge-dispatcher.yml` (md5 `9886d8e44dc2`), carries that probe, and its job is exactly the window measured on `opencharly/action-review#10`: the reusable is fired by `workflow_run` on the validator's **completion**, which happens *before* the native auto-merge that same validator arms — so without a wait, the sweep scans a `main` that does not yet contain the merge.

Measured on PR #17: `validate / validate` completed 16:49:53Z → sweep 16:49:56Z (head `2aa1aad`, pre-merge `main`) → merge lands 16:50:05Z (`35d202c`). A **9-second** race, lost. No `push`-event run exists for `35d202c` either, and the org reference's own header explains why: auto-merge squash merges produce **zero** workflow runs (platform-level suppression), so `push` and `pull_request: [closed]` cannot observe them.

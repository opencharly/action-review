# 2026.294.2356 — feat(rulebook)!: the coordination grammar shares no token with the verdict vocabulary

## Summary

`charly.yml` is the committed mirror of the live `AI_REVIEW_PROMPT` org variable — the rulebook the
validator enforces. It carried `BLOCKS` in BOTH senses:

- **verdict prose**, eleven times — "a change contradicting its owning skill BLOCKS", "these gates
  BLOCKS regardless of CI status". This is the validator saying *this finding blocks the merge*.
- **coordination labels**, three times — "`BLOCKS` comment naming both sides must exist", "A
  `CLAIM`/`TAKING OVER`/`HANDING OVER`/`BLOCKS` is addressed to the ACCOUNTABLE PARENT session", and
  the closed-set enumeration "`CLAIM`, `OWNING`, `HANDING OVER`, `TAKING OVER`, `BLOCKS`, `UNBLOCKS`,
  `STATUS`, `RESOLVED`".

One token, two meanings, in the same file — so a coordination comment announcing a dependency reads
like a verdict announcing a rejected PR. The fix is to make the coordination grammar share **no**
token with the verdict vocabulary. The coordination closed set becomes nine labels:

    CLAIM · OWNING · HANDING OVER · TAKING OVER · WAITING · HOLDING · CLEARED · STATUS · RESOLVED

`BLOCKS` splits by direction, so the first line states which side is speaking instead of leaving it
to be inferred from the body: `WAITING` is the blocked side ("I am waiting on you"), `HOLDING` is the
blocking side ("I am holding you up"). `UNBLOCKS` becomes `CLEARED`. The validator's own verdict
vocabulary (`PASS` / `BLOCK` / `FAIL` / `INCONCLUSIVE`) is untouched.

The three coordination sites change, and the eleven verdict sites do not:

| Site | Change |
|---|---|
| the COORD check (`:458`) | a `WAITING`/`HOLDING` comment naming both sides must exist, and a coordination comment opens with one of the nine closed-set labels and nothing else |
| the parent-addressing sentence (`:597`) | `BLOCKS` → `WAITING`/`HOLDING` in the list of labels addressed to the accountable parent session |
| the closed-set enumeration (`:599-600`) | the eight-label set → the nine-label set |

**The closed set, stated in full.** A coordination comment opens with one of the nine labels and
nothing else, and a comment whose first non-blank line is any other word is not a coordination comment,
so the COORD check does not count it. There is no exception and no grace period: a label outside the
set is simply not a coordination comment, and a thread that was answered under the old labels is
answered again in the new grammar.

**What changed in this round.** The first version of this PR carried a dated grandfather clause: a
coordination comment opening with a legacy label would be honoured when it was created strictly before
`2026-10-24T00:00:00Z`. Two of the three fresh validators on this PR blocked it — a dated read path for
the old labels is a legacy path surviving in the shipped rulebook, and the cutover policy sanctions no
grace period — and the clause contradicted the sentence beside it. The clause is GONE in this commit:
the grammar is a pure hard cutover, nine labels, no exception, no date. The tooling closes its sets in
the same cutover (legs 4 and 5) and never carries a legacy label.

**This is one leg of a six-repo cutover, not the whole of it.** The contract being cut over — the
coordination grammar — lives in six repos, and the producer-first pin contract forces the order: a pin
may only point at a MERGED ref, so the authored sources land first, the corpus that is GENERATED from
their tags follows, and the umbrella's gitlinks follow the corpus. That is the DECOMPOSITION axis of the
cutover policy — one contract, ordered units, scope never narrowed — and the tracking issue
`opencharly/opencharly#567` stays open until the last unit lands.
